## Implementation

The existing Explore map, panel/drag interaction, segmented control and BottomNavBar remain in place. Recommendation has its own ordered service results, Destination/category, Open at Night and minimum reviewed-rating filters, a search field with clear, horizontal galleries, and the shared destination footer. It expands using the existing panel behavior on selection; it does not add another screen or gesture system.

`mobile/index.js` currently registers `App.js`; the Expo Router route files are not the active entry. PB12 therefore uses the existing App `onOpenDetail(poi)` handoff to `PoiDetailScreen`, preserving `poi.id`. It does not migrate the application to Router. App owns the recommendation session and filter/search/segment state so opening detail and returning does not discard them. FlatList scroll offset is retained in the session. Nearby's existing API/filter behavior remains separate.

Save uses App's existing session bookmarks. Directions forwards the same POI with its coordinates to existing navigation; it is disabled with an explanation when coordinates are missing. The current itinerary handler previously announced success without storing anything; it now shows an accessible notice that the destination has **not** been added. Bookmark navigation stays on its existing handler. No replacement itinerary/bookmark module was built.

Photo sources: `imageUrl` and `images[].imageUrl`, already provided by the POI API/image integration. Recommendation service responses should include that same metadata. Development examples borrow images by stable ID from the already loaded POI catalogue, when present; they do not use the catalogue to calculate or rank recommendations. Photo fallback never invents destination imagery. Plus Jakarta Sans is local and OFL-licensed. Shared palette/icons remain consistent with main; the native map is not a Figma screenshot.

## Recommendation owner handoff

No recommendation function/endpoint exists on the fetched main. Search/listing POIs is not a contextual recommendation service. Production shows “Rekomendasi belum tersedia” until the service below is supplied. No algorithm is invented by PB12.

Optional mobile environment variable (no credential):

```env
EXPO_PUBLIC_RECOMMENDATIONS_PATH=/api/recommendations
```

This is a **proposed integration path**, not a backend endpoint added by PB12. Set it only when the owner implements the contract. Requests go to the existing `API_BASE_URL` plus this relative `/api/...` path. An absent path results in an explicit unavailable state, without a network request. HTTP failures, malformed payloads and timeouts expose retry, without replacing results with all POIs.

Request: `GET` to the configured path, optionally with `latitude` and `longitude` from a fresh, accurate foreground sample. If location is unknown, omitted or denied, the service must either return valid context-independent results according to its own policy or an empty result; it must not require the UI to invent coordinates. Context is sampled on initial load/manual refresh. GPS updates do not cause repeated recommendation requests. Filtering is local to the returned result, preserving response order.

Response:

```json
{
  "items": [
    {
      "poi": {
        "id": "P03",
        "name": "Sweet Cantina",
        "category": "Kuliner (Dessert)",
        "latitude": -6.91685,
        "longitude": 107.60895,
        "shortDescription": "Deskripsi dari sumber POI",
        "rating": 4.5,
        "reviews_count": 890,
        "images": [],
        "openAtNight": true
      },
      "reason": "Alasan dari pemilik service, jika ada"
    }
  ],
  "capabilities": { "openAtNight": true }
}
```

The example illustrates schema, not a contextual result. `id` and `name` are required; IDs must be unique. Optional fields follow the existing POI contract and pass through to detail. `imageUrl`, `images`, `description`, `history` and other detail fields can be supplied unchanged. The response order is authoritative. No sorting/randomization occurs in the UI. Rating only displays when `reviews_count > 0` and `0 < rating <= 5`; missing review metadata never implies a 5.0 rating.

The recommendation owner must define and provide `openAtNight` as a structured boolean and advertise the capability before that filter is enabled. PB12 does not parse `opening_hours` or assume that a time-category string means currently open. Category and reviewed-rating filters are applied only to returned recommendations.

No secrets are needed in mobile. Database credentials remain in the backend. No Supabase schema, RLS, coordinate or data migration is needed by PB12.

## Running and trying the feature

```sh
cd /Users/acit/Documents/MyWork/bragam-app-pb12/mobile
npm ci
npm start -- --clear
```

Use Android Expo Go/development build matching SDK 58; choose a free port if another checkout is running (`npm start -- --port <port>`). For actual backend/photos, set `EXPO_PUBLIC_API_URL` to the backend address reachable from the device. A backend is not required to try the explicitly labelled development response.

1. Open Explore → Recommendation.
2. Without a configured recommendation path, confirm the unavailable message.
3. In a development build, open **Skenario uji development** → **Contoh daftar**. The list is explicitly labelled as a UI example, not contextual recommendations. Example response order is P03 → P01 → P04; identities/names are derived from the repository CSV, with intentionally missing optional metadata for fallback coverage.
4. Try search/clear, Destination, Open at Night and Top Rated. Open Check Detail and go back; query/filters/results remain. Save uses current in-memory bookmarks. Add to Itinerary explains the unavailable integration.
5. Try **Contoh kosong** and **Contoh gagal**, then retry. **Service** switches back to the real configured integration. Demo loading lasts briefly so the loading state can be inspected.

The developer response loader is behind `__DEV__` and is not a production recommendation source. The existing PB05 fixture/controller files are left intact.
